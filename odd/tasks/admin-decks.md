## Specs

- **S1 — Administrative panel.** User: "necesitamos tener un panel donde poder crear mazos, sería un panel de admin." Latest authorization: "ahora comenzá con el desarrollo del panel de admin". Provide `/admin` to create and inspect managed decks, see generation progress, inspect cards, and control exclusions. Preserve the existing game UI and three seeded decks.
- **S2 — Environment-based login.** User: "Por otra parte se va loguear con user y contraseña que estarán como variables de entorno". Use server-only `ADMIN_USERNAME` and `ADMIN_PASSWORD`, plus `ADMIN_SESSION_SECRET` for expiring signed sessions. Missing credentials disable admin access, never grant it. All admin data and mutations require authorization; unsafe requests require same-origin protection. Never expose credentials or provider keys to clients or logs. Test invalid credentials, expired/tampered sessions, authorization and cross-origin rejection.
- **S3 — Automatic generation and replacement.** User: "Tiene que estar todo automatizado y el admin va poder ver que cartas son dudodas y decidirá reeplazarla, pero el reemplazo también será atumatizado." Generation and replacement run as bounded, persisted jobs, not request-owned promises. Replacement generates a different objective and preserves the old card until the new result is stored. Expose progress and failures without losing completed work.
- **S4 — Doubtful cards.** User: "Las cartas dudosas tienen que quedar excluidas automaticamente, el admin podrá quitar la exclusión o solicitar reemplazo". Excluded cards never enter the public playable projection. Manual inclusion is recorded separately from validation findings and cannot fabricate missing forbidden words. Regeneration does not silently clear findings on an unrelated card. Tests must prove exclusion and explicit override behavior.
- **S5 — Flash only.** User: "Entonces lo vamos hacer solo con deepseek flash". Use exactly `deepseek-flash` for generation and replacements; no Jev, Pro, or automatic model fallback. Generate up to 12 candidates per objective, explicitly ordered best to worst, then retain the first six valid candidates without score or confidence thresholds. New initial requests return batches of up to 50 complete card proposals per S12, including objectives and candidates; replacement/completion context remains per card. Bound provider calls and attempts; retain actual usage. No paid calls in automated tests.
- **S6 — Single written words.** User: "Las palabras prohibidas no deberían ser solo una palabra? me refiero a que no sean palabras compuestas"; confirmed "claro" after clarification that closed compounds are allowed. Reject phrases, empty terms, duplicates within a card and the objective itself. Different objectives may share useful prohibited words. Preserve Flash order after filtering and compare duplicates using the existing normalization helper. Test the public selection interface, including spaces, accents and duplicates.
- **S7 — Spanish validation.** User: "Y cómo podemos hacer para que no se guarden palabras que tienen ese tipo de errores" and "instalalo y hace una pruebaç". Reuse installed `nspell` + `dictionary-es` before accent-stripping normalization. Keep original spelling in the administrative record, never auto-correct suggestions, and keep unrecognized words out of playable cards unless the administrator explicitly overrides a complete doubtful card. A dictionary finding is not proof of semantic invalidity. Tests include `jaule`/`jaula` and `nectar`/`néctar`.
- **S8 — Existing runtime compatibility.** The requested panel extends the existing game, not its contracts. Use new administrative collections and project only eligible cards into the existing deck shape by stable ID, never name-based upsert or mutation of seed decks. Existing games already snapshot cards. Preserve canonical game normalization; dictionary validation operates on originals. No destructive migration or changes to existing command output. Document configuration and startup behavior in README and `.env.example`.
- **S9 — Live administrative progress.** User: "quiero que se use socketio para que el admin vea en tiempo real el progreso". Replace browser timer polling with authenticated Socket.IO progress delivery, reusing the existing custom server. Report persisted running/progress/terminal changes and recover an authoritative snapshot on initial subscription and reconnection. Keep game sockets and administrative data isolated; preserve durable jobs, existing HTTP actions and session/origin protections. Check real socket authentication, reconnect recovery, terminal updates and absence of browser polling without paid provider calls.
- **S10 — Login presentation.** User: "además mejorar la pantalla de login". Correction: "En la pantalla de login queda descolocado el link "Volver al juego"." Integrate that navigation into the login card instead of leaving an isolated link outside it. Improve the login's visual hierarchy, responsive presentation and form usability consistently with the game's existing design system, retaining Spanish UI copy and accessible labels, loading/error/unconfigured states and the current environment-based authentication. Do not add registration, change credentials or persist secrets in browser storage. Check the existing login behavior and the new interactions through the rendered form.
- **S11 — Administrative tabs.** User: "En el panel tenemos que usar tabs ("Crear mazo" | "Mazos")". Separate creation and deck management into these two accessible tabs, preserving creation inputs, existing deck actions and the live progress subscription across tab changes. Retain the catalog as the initial view to preserve existing entry behavior; show the managed deck after creation. Progress remains visible independently of the selected tab.
- **S12 — Generation scale and provider batches.** User: "En el panel el limite es hasta 50 cartas, el límite que le vamos a poner es de 1200 cartas, pero internamente lo vamos a procesar por lotes de 50 cartas". Clarification: "por ejemplo si en el panel se solicita 800 cartas, internamente vamos a solicitar por lotes de 50 palabras hasta completar las 800". Accept integer quantities from 1 through 1200 consistently in creation, additional generation, HTTP and application validation. New jobs request at most 50 complete cards per provider call, with only the remaining amount in the final call: 800 requires 16 full batches, 1200 requires 24 when responses are complete. Short/duplicate responses use bounded recovery and must never report completion below the requested total or generate beyond it. Preserve per-card dictionary findings/exclusions, replacement semantics, persisted progress, call reservations and existing jobs' stored batch sizes/budgets.
- **S13 — Complete recoverable deck CRUD.** User: "Falta CRUD para los mazos"; reply "dale" to the recommendation of recoverable archiving rather than permanent deletion. Keep create/list/detail, add editing of name/theme, archive with confirmation, archived-deck visibility and restoration in the existing `Mazos` tab. Preserve cards, findings and job history; archiving hides the deck from new games and restoring republishes eligible cards under the same stable public ID. Existing games and seeded decks remain untouched. Block metadata/archive/restore changes against queued or running generation; archived decks cannot enqueue generation/replacement or change cards until restored. Reuse environment-session/origin guards and the application's 80/200 metadata limits. Do not add permanent deletion, seeded-deck editing or manual card-text CRUD.

Implementation safeguards (not additional product scope): persisted bounded jobs with leases and fencing against stale writes; one active job per managed deck; server-owned HTTP calls; rate-limited login; safe shutdown; mocked provider tests and isolated Mongo probes. Missing Mongo/provider configuration is an explicit unavailable state, not successful generation. A managed deck with no eligible cards is not playable. New provider batches use at most 50 cards per S12; stored legacy jobs keep their own limits. The panel manages newly authored decks; the seeded decks remain unchanged.

- **S14 — Optional proper names and titles.** User: "Hay otra cosa que tenemos que tener en cuenta, por ejemplo hay veces en las que la palabra a adivinar será un nombre propio, por ejemplo el nombre de una serie como Juego de tronos. Correction: "Cuando se selecciona permitir nombres propios y titulos, las palabras prhibidas no deberán pasar por el diccionario porque muchas de ellas seran nombres propios". When enabled, accept multiword objectives such as `Juego de tronos`, do not reject proper-name objectives solely for dictionary absence, and do not consult the dictionary for forbidden candidates. Keep six individual forbidden words in provider order, rejecting empty terms, phrases, normalized duplicates, objective components and previously proposed terms. This is the explicit opt-in exception to S7; dictionary recognition must not be fabricated for unchecked words. With the option absent/false retain all existing dictionary validation and output. Apply to generation, completion and replacement; no retroactive card changes, game modifications or provider batch-size changes. Check enabled unknown proper-name forbiddens, zero candidate dictionary calls, structural filtering, insufficient-word exclusion, disabled preservation and provider instructions.
